# 「星を聴く」少数星・天体方向計算の技術検証

- 文書版: 0.2
- 検証日: 2026-09-06
- 対象: 北極星、シリウス、ベガを使う最初の端末内プロトタイプ
- 対象外: UI、音源制作、星座線、配布・申請、既存アプリ

## 1. 先に固定する判断

1. 天体方向は、位置・UTC日時・恒星の赤経/赤緯から端末内で計算する。画像認識を成立条件にしない。
2. アプリ内部の水平座標は **方位角 0°=真北、90°=東、時計回り**、高度は地平線 0°、天頂 +90° とする。経度は東経を正とする。
3. 方位角差だけで「近さ」を判定しない。星方向と端末照準方向を同じ3次元単位ベクトルにし、大円角距離で判定する。これは 0°/360° 境界と天頂付近でも安定する。
4. 初期プロトタイプの決定論的計算契約を「v0近似」として本書に固定する。v0はSIMBADのICRS/J2000座標を固定値としてUSNOの近似GASTに直接入れる。これは回帰試験用 fixture であり、商用出荷データの採用を意味しない。また、歳差・章動等をすべて入れた見かけ位置ではない。
5. 星を増やす前に、IAU SOFAを独立オラクルにした比較を行う。v0近似の許容差は方向ベクトル角距離 0.6°、本番候補の目標は 0.1°以下とする。個別の方位角差は天頂で発散するため合否指標にしない。
6. 端末姿勢は、利用可能ならCore Motionの `.xTrueNorthZVertical` を唯一の世界基準にする。そこへ `CLHeading.trueHeading` を再加算しない（二重の偏角補正になる）。`CLHeading` は精度判定とフォールバック用とする。
7. 「発見」は画像で星を同定した意味ではなく、**計算方向とセンサー推定の照準が一致した**という意味に限定する。発見できる方位品質は good/fair だけとし、approximate は粗い案内だけ、unavailable は全方向案内を停止する。
8. ライブ発見は幾何高度2°以上だけに許す。0°未満は自動で練習へ切り替え、0°以上5°未満は低高度警告を表示する。0°以上2°未満はライブ方向案内を許しても発見させず、2°以上5°未満の結果は地形・大気差の影響が大きい不確実帯として通常の屋外合否から分ける。

## 2. 座標と単位の契約

| 量 | 記号 | 単位・範囲 | 規約 |
|---|---:|---:|---|
| 赤経 | α | 時、`[0, 24)` | ICRS/J2000、1時=15° |
| 赤緯 | δ | 度、`[-90, +90]` | 北を正 |
| 緯度 | φ | 度、`[-90, +90]` | 北緯を正 |
| 経度 | λ | 度、`[-180, +180]` | 東経を正 |
| 局地時角 | H | 度、`[-180, +180)` | 子午線より西を正 |
| 方位角 | A | 度、`[0, 360)` | 真北0°、東90°、時計回り |
| 高度 | a | 度、`[-90, +90]` | 地平線0°、上を正 |

すべての三角関数へ渡す前にラジアンへ変換する。剰余は言語の `%` を直接信頼せず、負数でも正になる定義を使う。

```text
wrap360(x) = ((x % 360) + 360) % 360
wrap24(x)  = ((x % 24)  + 24)  % 24
wrap180(x) = wrap360(x + 180) - 180     // [-180, 180)
```

注意:

- v0近似では固有運動、視差、動径速度を適用しない。シリウスは3星中で固有運動が大きいが、J2000から26年の固有運動量は合成して約35秒角（約0.010°）で、現段階の磁気方位誤差より十分小さい。
- 一方、J2000固定座標と日付の見かけ座標の差には歳差・章動・年周光行差も含まれる。v0の「0.6°」は実装の正確さではなく、少数星・現代の日付範囲に置く検証用上限である。期限を設けずに固定J2000を使い続けてはならない。
- Polarisは多重星かつ変光星として登録されている。プロトタイプでは上表の主対象座標を一つの探索方向として扱う。

## 4. v0近似の計算仕様

### 4.1 UTCからJulian Date

Foundationの `Date` をPOSIX UTC秒として扱う場合は次でよい。

```text
JD_UTC = unixSeconds / 86400 + 2440587.5
```

検算値:

| UTC | JD_UTC |
|---|---:|
| 1970-01-01T00:00:00Z | 2440587.5 |
| 2000-01-01T12:00:00Z | 2451545.0 |
| 2026-01-15T12:00:00Z | 2461056.0 |

端末時計にはUTCを使う。天体計算に本来必要なUT1について、v0では `UT1=UTC`、`TT=UTC` と近似する。IERSの現行方式では `|UT1-UTC|<0.9秒` に保たれるため[S5]、地球回転角への最大寄与は約0.00375°で、iPhone磁気方位誤差よりはるかに小さい。うるう秒そのものの文字列 `23:59:60` はFoundationの通常日時入力に作らず、システム時刻へ委ねる。

v0式の使用範囲は、USNOが誤差を示している2000-01-01〜2100-12-31に制限する。範囲外を暗黙に外挿しない。また、端末時計自体が1分ずれると恒星方向は最大約0.25°、4分なら約1°ずれる。通信なしでは時計の真偽を独立確認できないため、デバッグ画面と屋外試験記録には計算に使ったUTCを必ず表示する。

### 4.2 Greenwich apparent sidereal time

USNOの近似式[S1]を採用する。ここで `JD0` は直前の0時UTのJD、`hUT` はそこからのUT時間である。

```text
JD0  = floor(JD_UTC - 0.5) + 0.5
hUT  = (JD_UTC - JD0) * 24
D0   = JD0    - 2451545.0
DTT  = JD_UTC - 2451545.0
T    = DTT / 36525

GMST_h = wrap24(
    6.697375
  + 0.065709824279 * D0
  + 1.0027379      * hUT
  + 0.0000258      * T^2
)

Omega_deg = 125.04 - 0.052954 * DTT
L_deg     = 280.47 + 0.98565  * DTT
eps_deg   = 23.4393 - 0.0000004 * DTT

dPsi_h = -0.000319 * sin(Omega_deg)
         -0.000024 * sin(2 * L_deg)
eqeq_h = dPsi_h * cos(eps_deg)
GAST_h = wrap24(GMST_h + eqeq_h)
```

上の `sin` / `cos` では度をラジアンへ変換する。USNOは2000〜2100年でこの近似GASTの最大誤差を0.432秒（時刻）、RMSを0.01512秒としている[S1]。0.432秒時は天球上で約0.0018°である。

局地恒星時と時角は次の通り。

```text
LST_deg = wrap360(GAST_h * 15 + longitudeEast_deg)
H_deg   = wrap180(LST_deg - RA_h * 15)
```

### 4.3 時角・赤緯からENU方向、方位角、高度

USNOの高度・方位角式[S2]と同値だが、象限処理と後段の角距離計算を安全にするため、まず東・北・上（ENU）単位ベクトルを作る。

```text
E = -cos(delta) * sin(H)
N =  sin(delta) * cos(phi)
   - cos(delta) * cos(H) * sin(phi)
U =  sin(delta) * sin(phi)
   + cos(delta) * cos(H) * cos(phi)

altitude = atan2(U, hypot(E, N))
azimuth  = wrap360(atan2(E, N))
```

`atan2(E,N)` の引数順は意図的である。この順で北が0°、東が90°になる。丸めでベクトル長が1からずれた場合は正規化する。`hypot(E,N)` が十分小さい天頂・天底では方位角を未定義として扱い、直前値で判定してはならない。

USNO記載の直接式との照合にも次を使える。

```text
sin(a) = cos(H) cos(delta) cos(phi) + sin(delta) sin(phi)
A = atan2(
    -sin(H),
    tan(delta) cos(phi) - sin(phi) cos(H)
)
```

### 4.4 地平線下判定

計算値は大気差を含まない幾何高度とする。

```text
mathematicalBelowHorizon = altitude_deg < 0
```

浮動小数の単体試験では `abs(altitude)<=1e-9°` を地平線境界とみなす。製品表示と発見可否は次の4状態に分ける。

| 幾何高度 | 表示・動作 |
|---:|---|
| `< 0°` | 「地平線の下」。ライブから自動で明示された練習へ切り替え、ライブ発見を禁止 |
| `0° ... < 2°` | 「低い空」。警告付きライブ方向案内は可、ライブ発見は禁止 |
| `2° ... < 5°` | 「低い空」。good/fairならライブ発見可。ただし地形・建物・大気差の影響が大きく、通常の屋外合否とは分ける |
| `>= 5°` | 方位品質条件を満たせば通常のライブ探索・発見可 |

平均的な水平大気差には34分角（0.5666°）が採用されるが、気圧・気温等で変わる[S15]。したがって、見える/見えないの厳密判定に固定の大気差を足すより、地平線付近を不確実帯として扱う方がこのアプリには安全である。建物・山・樹木は計算できない。

Core Locationの緯度・経度はWGS 84の測地座標としてそのまま使う。恒星までの距離に対し観測者高度は方向計算上ほぼ無視できるが、高所から見た水平線の俯角や局地地形には影響する。本書の `altitude<0` はあくまで観測点の局所水平面に対する数学的判定であり、実際の地形上の可視性ではない。

## 5. 方向差と「近づいた」の計算

方位角 `A`、高度 `a` をENUへ変換する。

```text
v(A,a) = (
  cos(a) * sin(A),   // East
  cos(a) * cos(A),   // North
  sin(a)             // Up
)
```

星方向 `s` と端末照準方向 `p` の角距離は、`acos(dot)` より0°/180°近傍でも安定する形を使う。

```text
gamma = atan2(length(cross(s, p)), dot(s, p))  // 0...pi
```

それぞれ単位化し、内積を使う実装では `[-1,+1]` にclampする。補助表示用の符号付き水平差は次でよい。

```text
deltaAz = wrap180(A_star - A_aim)
deltaAlt = altitude_star - altitude_aim
```

ただし、端末がロールしている場合の「耳の左右」は `deltaAz` では決めない。星の世界ベクトルを端末座標へ変換し、その左右成分から立体音を作る。

- 同じ定数・同じv0式の単体試験: `H/A/a ±0.001°`、各ベクトル成分 `±1e-6`。

### 6.3 地平線境界

同じ日時・地点で、人工星 `δ=0°` の時角を変える。西側地平線なので `H=+90°` が境界になる。

|---:|---:|---:|---:|---|
| +89.9° | 22.988100598205 | 269.941672° | +0.081227° | above |
| +90.0° | 22.981433931538 | 270.000000° | 0.000000° | boundary |
| +90.1° | 22.974767264871 | 270.058328° | -0.081227° | below |

これで符号、東西、`<0` 判定の逆転を検出する。

### 6.4 角距離の境界試験

| 星 `(A,a)` | 照準 `(A,a)` | 期待 `deltaAz` | 期待 `gamma` | 目的 |
|---|---|---:|---:|---|
| `(359°,0°)` | `(1°,0°)` | -2° | 2° | 0/360° wrap |
| `(359°,30°)` | `(1°,30°)` | -2° | 1.732029° | 方位角差と大円距離が別物 |
| `(0°,90°)` | `(217°,90°)` | 未使用 | 0° | 天頂では方位角が未定義 |
| `(149.710021°,31.873653°)` | 同値 | 0° | 0° | 一致 |
| `(0°,0°)` | `(180°,0°)` | -180° | 180° | 反対方向 |

角距離の単体試験許容差は `±1e-6°` とする。

### 6.5 現行Swift実装の位置づけ

現行の `AstronomyCalculator` は、上の固定J2000 v0式をそのまま製品化したものではない。3星の固有運動、IAU 2006 P03のbias-precession、Earth Rotation AngleとGMST06を使って平均日付座標へ進める。`UT1=UTC`、`TT-UTC=69.184秒` は固定近似で、章動、年周光行差、視差、大気差はまだ入れない。

共通入力で現行実装と6.2のv0 fixtureを比較した方向角距離は、北極星 `0.147638°`、シリウス `0.281670°`、ベガ `0.173315°` だった。これは変更量が初期の `0.6°` 枠内であることを示す互換確認にすぎず、天文学的な正しさを独立に証明しない。`tools/validate_reference.py` も係数と期待値をリポジトリ内で照合する回帰試験であり、SOFAオラクルではない。

## 7. 本番精度へ上げるための独立オラクル

IAU SOFAは、IAU承認モデルを実装・検証する権威あるライブラリで、IAU 2006歳差とIAU 2000A章動を扱う[S3][S4]。ネット接続を製品へ追加する必要はなく、開発時の期待値生成器として使える。

比較条件を曖昧にしないため、オラクル側は次を固定する。

1. SIMBADのICRS/J2000座標、固有運動、視差、動径速度を入力する。
2. UTCからTT/UT1へ変換する。オフライン製品との公平な比較ではまず `DUT1=0` とし、別試験でIERS値を与える。
3. IAU 2006/2000AでICRSから日付の中間/見かけ方向へ変換する。
4. 同じWGS 84緯度・東経を使う。極運動 `xp=yp=0`、気圧 `0 hPa` として真空の幾何方向を得る。
5. 方位・高度の個別差ではなく、双方をENUベクトルへ戻した角距離を比較する。

推奨のSOFA経路は、カタログから観測方位/天頂距離まで扱う `iauAtco13` 相当、またはICRS→CIRSのastrometry routinesと時角→方位高度変換の組合せである。SOFAコード/アルゴリズムを製品へ移植する場合は、名称・派生表示等を含むSOFAライセンス条件を別途満たす必要がある（[S3]からTerms and Conditionsを参照）。単なる試験オラクル利用と製品へのコード移植を区別する。

合格基準:

| 段階 | 対象日時/地点 | 高度条件 | SOFAとの方向角距離 |
|---|---|---:|---:|
| v0少数星検証 | 2025-01-01〜2030-12-31、四季各2日時、東京・札幌・那覇 | `a>=5°` | `<=0.6°` |
| 本番候補 | 同上 | `a>=5°` | `<=0.1°` |
| 地平線下境界 | 同上 | `-2°<=a<0°` | 数値と自動練習への切替を記録し、ライブ発見は禁止 |
| 低高度境界 | 同上 | `0°<=a<=5°` | 数値と0°/2°/5°の状態遷移を記録するが、可視/不可視や通常成功率の受入判定には使わない |

現行Swift実装には歳差と固有運動を先行して入れているが、SOFAとの独立グリッド比較は未実施である。v0または現行実装が0.6°を超えるケースを見つけた時点で、星を増やす前にモデルを修正する。0.6°以内でも、リポジトリ内の自己整合だけを最終版の精度保証にしてはならない。

## 8. Core LocationとCore Motionの統合

### 8.1 推奨経路

```text
星のRA/Dec + UTC + location
          -> 星のENU単位ベクトル s_ENU

Core Motion .xTrueNorthZVertical + 端末固定の照準軸
          -> 照準ENU単位ベクトル p_ENU

s_ENU と p_ENU
          -> 大円角距離 gamma、端末座標の左右/上下成分
```

Appleによると `.xTrueNorthZVertical` はX軸を地理的北、Z軸を鉛直とする。利用には磁力計と位置情報が必要で、未較正なら端末移動を促す[S6]。開始前に `availableAttitudeReferenceFrames()` を確認する。

重要:

- `.xTrueNorthZVertical` 使用中は、その姿勢に真北基準がすでに入っている。`trueHeading-magneticHeading` や `trueHeading` をyawへ足さない。
- Core Locationの `trueHeading` は位置更新が有効な場合だけ有効で、負値は無効[S7]。`headingAccuracy` も負値なら無効で、正値が小さいほど良い[S8]。
- `headingAccuracy` は補正量ではない。方位に加減算せず、品質ゲートと不確実性表示に使う。
- `course` は移動方向であって端末の向きではないため使用しない。

### 8.2 軸と照準の固定

Appleの端末座標図では、iPhoneの `+X` は画面右、`+Y` は画面上端、`+Z` は画面表から外向きである[S11]。背面カメラが見る方向を照準にする本アプリでは、端末座標の照準軸は原則 `q_device=(0,0,-1)` とする。上端を指し棒のように使う別モードを作るなら `+Y` であり、同じモード内で混ぜない。

`.xTrueNorthZVertical` の参照座標は、右手系から `(X,Y,Z)=(North,West,Up)` と解釈できる。ENUからの並べ替えは次になる。

```text
v_reference = (N, -E, U)
```

ただしAppleの公開説明は `CMRotationMatrix` の「どちら向きに掛けるか」まで十分明記していない[S9]。転置・符号を推測だけで確定せず、次の姿勢試験で固定する。仮に `R` が参照→端末を表すなら `q_reference = transpose(R) * q_device` であり、逆規約なら `R*q_device` になる。

必須の軸受入試験:

| 端末姿勢（静止） | 背面カメラ照準の期待 |
|---|---|
| 画面を下、背面を真上 | 高度 +90°、方位角は未定義 |
| 縦持ち、画面を南向き | 真北 A=0°、高度0° |
| 縦持ち、画面を西向き | 真東 A=90°、高度0° |
| 縦持ち、画面を北向き | 真南 A=180°、高度0° |

各姿勢は金属机で行わず、非磁性の治具と独立した真北基準を使う。この4試験に通るまで星方向との統合を始めない。Euler角のyaw/pitchを個別に組み替えるより、quaternion/回転行列と固定照準軸を使う。

### 8.3 フォールバック

優先順:

1. `.xTrueNorthZVertical` が利用可: 正規経路。`CLHeading` は品質確認のみ。
2. `.xMagneticNorthZVertical` のみ: 同時刻に近い有効な `trueHeading` と `magneticHeading` の差で世界Z軸回りを一度だけ補正する。符号は上記4姿勢試験で確定する。
3. `.xArbitraryCorrectedZVertical` のみ: 有効な `trueHeading` で初期アンカーを作れるが、再アンカーとドリフト評価が必要。発見演出を許す本番経路にはしない。
4. 磁力計なし、真北が得られない、権限なし: 練習デモまたは画面説明へ降格し、正確な方向発見を表示しない。

`CLLocationManager.headingOrientation` をフォールバックで使う場合、Core Locationの方位は既定で縦持ち上端基準であり、設定変更後の値にのみ向きが反映される[S7の関連仕様]。一方、固定照準軸を回転行列で世界へ写す正規経路では、UIのportrait/landscape回転をもう一度加えない。

### 8.4 時刻同期と平滑化

- 現行実装のCore Motion更新は30 Hz、画面側の評価は10 Hzとし、描画/音処理は最新サンプルを使う。Appleもサンプルのtimestampで鮮度確認するよう案内している[S9]。
- 天体方向は1 Hz再計算で十分。恒星時の変化は約0.0042°/秒で、センサー誤差より小さい。
- `CMLogItem.timestamp` は起動後時間、`CLHeading.timestamp` は日時なので直接引かない。受信時に単調時計へ写すか、同一キューで受信時刻を付け、最も近いサンプルを組み合わせる。
- 現行の鮮度ゲートはmotion sample 0.25秒以内、heading 2秒以内とする。locationは受信時に60秒未満の候補だけを採用する。これらは単体試験と屋外記録で同じ境界を使う。
- 359°と1°を数値平均しない。将来平滑化を加える場合はquaternionまたは単位ベクトルを使い、再正規化する。平滑化を未実装のまま受入済みと書かない。
- 現行実装は歩行・走行・自転車・自動車の移動判定またはmotion sampleの陳腐化で全案内と発見保持を停止する。角速度による追加ゲートは屋外試験で必要性を判断する将来候補であり、現行の受入条件へ混ぜない。
- 発見の連続滞在時間は0.8秒とし、途中で品質、移動、鮮度、角距離、高度のいずれかが不適格になれば保持をリセットする。

## 9. 方位品質、8の字補正、磁気干渉

Appleは、Core Locationが地磁気の大きさ/傾きの大きな変化を検出した場合等に較正UIを出せるとしている。また、較正で除けるのは端末と共に動く磁場に限られ、外部磁場源の近くでは磁場源から離れる必要がある[S10]。

初期品質ゲート（Appleの保証値ではなく、本プロトタイプの工学値）。ここで `effectiveHeadingAccuracy` は有効な `headingAccuracy` とセンサー間残差を保守的にまとめた度数であり、真北不明、値の陳腐化、未較正、必要センサー欠落等は unavailable とする。

| 状態 | 条件 | 動作 |
|---|---|---|
| good | `0°<=effectiveHeadingAccuracy<=8°` | 通常案内。発見判定可 |
| fair | `8°<effectiveHeadingAccuracy<=10°` | 不確かさを表示しつつ案内。発見判定可 |
| approximate | `10°<effectiveHeadingAccuracy<=25°` | 「おおよその方向を案内しています」。誤差幅内は「このあたりです」。発見演出なし、周期は0.45秒以上、clarityは0.6以下 |
| unavailable | 有効値なし、負値、`effectiveHeadingAccuracy>25°`、真北不明、必要センサーなし、または陳腐化 | 音・触覚・画面方向案内と発見判定をすべて停止。安全な場所で補正/練習を案内 |

判定優先度は `unavailable > approximate > fair > good` とする。移動中またはmotion sampleが古い場合は、方位品質の表示値にかかわらず全案内と発見判定を停止する。位置精度は方向計算への影響を別途記録するが、方位品質の8°/10°/25°境界と混ぜない。

補正フロー:

1. 立ち止まり、車・スピーカー・MagSafeアクセサリ・金属柵・鉄骨から離れるよう案内する。
2. 周囲を確認してから、端末でゆっくり8の字を2〜3回描く。歩きながら行わせない。
3. OSの較正表示を許可し、3秒以上新しいサンプルを採る。
4. `headingAccuracy` と磁場較正状態が改善したか判定する。改善しなければ8の字を繰り返させず、場所を移すよう案内する。
5. 補正の前後で定数offsetを勝手に保存しない。環境磁場は場所で変わる。

車内、鉄骨建物、線路、金属柵の近くでは、数値上の `headingAccuracy` だけで全干渉を検出できる保証はない。「精度良好」でも星が一貫して横にずれるケースを実地試験で記録し、利用場所の警告を常に見られるようにする。

## 10. 発見判定の初期値

方位センサーの不確実性を隠さない。次をすべて満たすときだけ「計算方向との一致」を発火する。

```text
star altitude >= +2°
quality in {good, fair}
T = clamp(3° + effectiveHeadingAccuracy / 3, 3°, 6°)
gamma <= T continuously for 0.8 s
sensor data is fresh
device is not in unsafe motion
```

練習モードだけは高度条件を免除できるが、全画面で練習と明示し、ライブ発見履歴へ混ぜない。`T` は精度0°で3°、精度9°以上で上限6°となる。途中で一条件でも外れれば0.8秒保持をリセットし、発見は一度だけ発火する。音と触覚の近接マッピングは連続的な `gamma` を使い、方位角差・高度差ごとの段差を作らない。

この閾値はPhase 1の実装契約であり、屋外試験を通じて妥当性を評価する。`headingAccuracy=10°` は「実際に10°ずれている」という意味でも1σでもなく、Appleが報告する潜在誤差の指標である[S8]。変更する場合は実装、単体試験、本書、画面遷移、受入条件を同じ変更で更新する。

## 11. 実機検証と受入条件

### 11.1 実施条件

- G4の最低通過回数は[屋外実機テスト](08-field-test.md)と本書とは別の[MVP要件とデータ権利判断](REQUIREMENTS-AND-RIGHTS.md) A-FIELDを正本とする。以下の2機種・2夜・各星10回は、最低ゲート通過後に分布と再現性を評価する拡張検証である。
- 少なくとも2機種、2夜、各星10回以上。北極星とシリウスは高度15°以上の時間を選ぶ。ベガは地平線下ケースにも使う。
- 開けた屋外で静止し、車・電線設備・金属柵・鉄骨から10 m以上離れた地点を第一基準環境とする。
- カメラ中央へ実際の星を合わせる操作は**誤差測定の基準作り**にだけ使い、画像認識は使わない。中央時の `gamma`、方位精度、磁場較正、姿勢、時刻、位置精度を端末内の一時デバッグ表示で読む。
- 個人位置を外部送信しない。試験記録を保存する場合も座標は試験担当者が明示的に採取し、公開資料では丸める。
- 「探す」操作中に歩かせない。視線と周囲の安全を確認してから端末を向ける。

### 11.2 合格条件

| 項目 | 初期合格条件 |
|---|---|
| 純粋計算回帰 | 本書6章の全値が指定許容差内 |
| 数値性質 | 10,000件のランダム入力でNaNなし、ベクトル長誤差 `<=1e-12`、範囲規約を満たす |
| SOFA比較 | 7章のv0グリッドで方向角距離 `<=0.6°` |
| 軸統合 | 8.2の4姿勢すべてで期待象限が一致。good/fair時の角誤差中央値 `<=5°`、90パーセンタイル `<=10°` |
| 実星センタリング | good/fairサンプルで残差中央値 `<=6°`、90パーセンタイル `<=12°` |
| 発見再現性 | 各星10試行中9回以上、各サンプルの適応許容角 `T=3°...6°` 内を0.8秒保持して一度発見。15°より外では20掃引中誤発見0回 |
| wrap/天頂 | 0/360°を通過して音像が反転せず、天頂でNaN・急な方位反転なし |
| 地平線 | ベガの負高度ケースで自動練習、0°/2°/5°境界で警告・発見可否が仕様通り。0〜5°の結果は通常成功率と分ける |
| 干渉 | 車内・鉄骨付近の静止試験でapproximate/unavailable/警告または明白なずれを記録でき、不適格時は発見を確定扱いしない |
| 補正 | good/fairへ改善すれば通常誘導へ復帰。改善しない場合は8の字の無限要求をせず「場所を移す」へ遷移 |

中央値/90パーセンタイルは good/fair、すなわち `effectiveHeadingAccuracy<=10°` のサンプルだけで評価し、除外数も必ず報告する。良いサンプルだけを選んで除外率を隠さない。good/fair到達率が第一基準環境で80%未満なら、発見閾値を広げて済ませず、センサー統合または製品体験を再検討する。幾何高度2°以上5°未満は参考記録とし、通常成功率へ混ぜない。

## 12. 昼・曇天練習モード

- 昼または曇天でも、同じ方向計算とセンサー誘導を練習に使える。ただし完了文言は「方向が合いました」とし、「星が見えた」としない。
- ライブ選択時に幾何高度が0°未満なら、「今は地平線の下」と通知して明示されたシミュレーション日時の練習へ自動で切り替える。これは現在の実空方向への誘導ではない。
- 幾何高度0°以上2°未満のライブでは低高度警告と方向案内を出せるが発見不可とする。練習ではこの高度ゲートを免除できる。
- シミュレーション日時を使う場合、全画面に練習中であることを残し、実空の発見履歴へ混ぜない。
- 暗所AR/カメラ重畳は補助表示であり、この計算・センサー検証の合格条件には入れない。
